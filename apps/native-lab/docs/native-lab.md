# Native Lab — React Native 네이티브 기능 학습 프로젝트

## 1. 프로젝트를 시작하는 이유

React 개발 경험은 충분하지만 React Native는 아직 익숙하지 않다. 따라서 웹에서 이미 알고 있는 React 문법을 반복하기보다, React Native가 실제 디바이스와 연결되는 지점을 직접 경험하는 것을 목표로 한다.

이 프로젝트는 완성된 상용 앱을 만드는 것이 목적이 아니다. 다음 질문에 답할 수 있을 정도로 React Native의 기본기를 익히는 실험 프로젝트다.

- 모바일 앱에서 권한은 언제, 어떻게 요청하는가?
- 카메라나 파일 선택 결과는 어떤 형태로 들어오는가?
- 선택한 파일을 앱의 로컬 저장 공간에 어떻게 보관하는가?
- 웹의 상태 관리와 모바일 앱의 생명주기·OS 기능은 어떻게 연결되는가?
- React Native 화면과 WebView 안의 웹 화면은 어떤 방식으로 통신하는가?
- 같은 React Native 코드가 iOS와 Android에서 어디까지 동일하게 동작하는가?

앱의 주제는 사진·파일·메모를 남기는 **현장 기록 앱**으로 정한다. 기록이라는 도메인은 카메라, 파일, 로컬 데이터, 공유, 딥링크를 억지로 붙이지 않고 하나의 사용자 흐름으로 연결하기 좋다.

## 2. 학습 목표와 완료 기준

### 핵심 목표

1. Expo 기반 React Native 앱의 구조와 실행 방식을 이해한다.
2. 모바일 권한 요청과 권한 거부 상태를 처리한다.
3. 디바이스에서 얻은 사진·파일을 앱 내부 저장 공간에 보관한다.
4. 서버 없이도 앱을 재실행해 데이터를 유지한다.
5. OS가 제공하는 공유와 딥링크 흐름을 연결한다.
6. WebView를 보조 화면으로 사용하고 RN과 웹 간 Bridge를 구현한다.
7. iOS와 Android의 차이를 기능 단위로 기록한다.

### 완료 기준

- 카메라 또는 사진 보관함에서 이미지를 선택해 기록에 첨부할 수 있다.
- 문서 파일을 선택해 기록에 첨부할 수 있다.
- 앱을 종료했다 다시 실행해도 기록과 첨부파일 메타데이터가 남아 있다.
- 기록 목록에서 상세 화면으로 이동하고 기록을 삭제할 수 있다.
- 첨부파일을 OS 공유 시트로 보낼 수 있다.
- `nativelab://record/{id}` 형태의 딥링크로 특정 기록을 열 수 있다.
- WebView가 로드되고, 웹 → RN 및 RN → 웹 메시지가 오간다.
- 권한 거부, 파일 선택 취소, 저장 실패, WebView 로딩 실패를 사용자에게 설명할 수 있다.

## 3. 학습 범위

### 이번 프로젝트에서 다루는 내용

#### React Native 기본 구조

- Expo managed workflow의 앱 구조
- `View`, `Text`, `TextInput`, `Pressable`, `ScrollView`, `Image` 등 기본 컴포넌트
- `StyleSheet`와 모바일 화면 크기·Safe Area 대응
- 앱 상태와 화면 전환 상태 관리
- 키보드, 뒤로가기, 로딩·에러·빈 상태 처리

#### 네이티브 기능 핵심 5종

1. **카메라와 사진 선택**
   - 카메라 권한 및 사진 라이브러리 권한 요청
   - 촬영 결과와 선택 결과의 URI·파일 정보 처리
   - 권한 허용, 거부, 제한된 접근, 취소 상태 처리

2. **파일 선택과 앱 전용 파일 저장**
   - 문서 선택기에서 파일 선택
   - 임시 URI와 앱 내부 영구 저장 URI의 차이 이해
   - 파일명, MIME type, 파일 크기, 확장자 관리

3. **로컬 데이터 저장**
   - 기록과 첨부파일 메타데이터의 관계 모델링
   - SQLite CRUD
   - 앱 재실행 후 데이터 복원
   - DB 데이터와 실제 파일의 정합성 유지

4. **OS 공유**
   - iOS/Android 공유 시트 열기
   - 로컬 파일 URI를 다른 앱으로 전달
   - 공유할 수 없는 파일·환경에 대한 예외 처리

5. **딥링크와 WebView**
   - 앱 URL scheme 등록
   - 초기 딥링크와 앱 실행 중 딥링크 이벤트 처리
   - URL에서 기록 ID를 추출해 상세 화면 열기
   - WebView의 기본 navigation 제어
   - `window.ReactNativeWebView.postMessage`와 `injectJavaScript`를 통한 양방향 Bridge

- 결제와 인앱 구매
- 복잡한 전역 상태 관리 라이브러리

## 5. 요구사항

### 5.1 기능적 요구사항

#### 기록 관리

- 사용자는 제목과 메모를 입력해 새 기록을 만들 수 있어야 한다.
- 사용자는 기록 목록과 기록 상세를 확인할 수 있어야 한다.
- 기록은 생성일 또는 수정일 기준으로 정렬되어야 한다.
- 사용자는 기록을 삭제할 수 있어야 한다.
- 기록이 없을 때 빈 상태와 새 기록 생성 방법을 보여줘야 한다.

#### 사진·파일 첨부

- 사용자는 카메라로 사진을 촬영해 첨부할 수 있어야 한다.
- 사용자는 사진 보관함에서 이미지를 선택해 첨부할 수 있어야 한다.
- 사용자는 문서 파일을 선택해 첨부할 수 있어야 한다.
- 선택한 파일은 앱 전용 저장 공간으로 복사되어야 한다.
- 첨부파일의 이름, 종류, MIME type, 크기, 로컬 URI를 기록해야 한다.
- 파일 선택을 취소해도 작성 중인 기록이 깨지지 않아야 한다.
- 기록 삭제 시 연결된 첨부파일과 메타데이터도 함께 정리해야 한다.

#### 공유와 딥링크

- 첨부파일이 있는 기록은 OS 공유 시트를 열 수 있어야 한다.
- 공유 기능을 지원하지 않는 환경에서는 대체 안내를 보여줘야 한다.
- 앱은 `nativelab://record/{id}` URL을 처리해야 한다.
- 이미 실행 중인 앱과 종료 상태의 앱 모두 딥링크를 처리해야 한다.
- 존재하지 않는 기록 ID로 진입하면 오류 또는 목록 화면으로 안전하게 복귀해야 한다.

#### WebView

- WebView 보조 화면에서 정해진 웹 콘텐츠를 열 수 있어야 한다.
- 웹 페이지의 준비 완료 이벤트를 RN이 받을 수 있어야 한다.
- RN은 기록 개수 등 간단한 상태를 WebView에 전달할 수 있어야 한다.
- 웹에서 요청한 이벤트를 RN이 명시적인 메시지 타입으로 처리해야 한다.
- 허용하지 않은 외부 링크는 WebView 안에서 무분별하게 열지 않아야 한다.
- 로딩 중, 로딩 실패, 재시도 상태를 제공해야 한다.

#### 권한과 오류 처리

- 카메라와 사진 접근 권한 요청 전에 기능의 목적을 설명해야 한다.
- 사용자가 권한을 거부하면 기능을 사용할 수 없는 이유와 재시도 방법을 보여줘야 한다.
- 네이티브 API 실패를 앱 전체 오류로 확산하지 않고 해당 기능의 오류 상태로 처리해야 한다.
- 저장 중 중복 제출을 방지해야 한다.

### 5.2 비기능적 요구사항

- 초기 버전은 서버 없이 오프라인으로 동작해야 한다.
- 기록 내용과 첨부파일은 기본적으로 기기 내부에만 저장해야 한다.
- 공통 화면과 비즈니스 로직은 iOS/Android에서 공유해야 한다.
- 플랫폼별 차이가 필요한 코드는 명시적으로 분리하고 이유를 문서화해야 한다.
- 권한 거부·취소·네트워크 실패·파일 누락을 정상적인 사용자 상태로 취급해야 한다.
- 화면은 작은 iPhone부터 태블릿까지 내용이 잘리지 않아야 한다.
- 버튼, 입력창, 오류 메시지는 VoiceOver/TalkBack에서 이해할 수 있는 이름을 가져야 한다.
- 이미지와 파일의 크기를 고려해 불필요한 중복 복사와 메모리 사용을 피해야 한다.
- 네이티브 기능을 호출하는 모듈과 화면 UI를 분리해 테스트 가능성을 확보해야 한다.
- README 또는 학습 문서에 실행 방법, 실기기 테스트가 필요한 기능, 플랫폼별 차이를 기록해야 한다.

## 6. React Native에서 iOS와 Android를 다룰 때의 차이

React Native는 UI와 대부분의 로직을 공유할 수 있지만, 네이티브 기능은 운영체제의 정책과 파일 모델을 그대로 반영한다. “한 번 작성하면 어디서나 동일하게 동작한다”기보다 “공통 흐름을 만들고 플랫폼 차이를 명시적으로 처리한다”는 관점으로 접근한다.

### 6.1 권한

| 주제      | iOS                                                  | Android                                                    | 구현 시 주의점                                                    |
| --------- | ---------------------------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------- |
| 카메라    | `Info.plist`의 사용 목적 문구가 필요하다.            | Manifest 권한과 런타임 권한을 함께 고려한다.               | 권한 요청 자체보다 거부·영구 거부 상태가 중요하다.                |
| 사진      | 전체 사진 또는 제한된 사진 접근을 선택할 수 있다.    | Android 버전에 따라 사진/미디어 권한 정책이 달라진다.      | 선택된 자산이 일부만 보이는 상태를 정상 흐름으로 처리한다.        |
| 파일      | Files 앱과 document provider를 통해 파일을 선택한다. | `content://` URI와 Storage Access Framework를 자주 접한다. | URI를 곧바로 영구 경로로 가정하지 말고 앱 저장 공간으로 복사한다. |
| 설정 이동 | 앱 설정으로 이동하는 UX가 비교적 일관된다.           | 제조사별 설정 화면 차이가 있을 수 있다.                    | 설정 화면을 열지 못하는 경우에도 안내를 제공한다.                 |

### 6.2 파일과 저장 공간

- iOS는 앱 sandbox가 강하게 분리되어 있으며, 앱 컨테이너 밖의 파일을 직접 경로로 다루기 어렵다.
- Android는 버전별 scoped storage 정책 때문에 외부 저장소의 일반적인 경로 접근을 가정하면 안 된다.
- iOS의 `file://` URI와 Android의 `content://` URI가 다를 수 있다.
- 파일 선택 직후에 얻은 URI가 앱 재실행 후에도 유효하다고 가정하지 않는다. 필요한 파일은 앱 전용 저장 공간으로 복사하고, DB에는 복사된 URI를 저장한다.
- 큰 이미지의 경우 원본을 그대로 여러 번 복사하지 않고 크기·압축·캐시 정책을 별도로 정한다.

### 6.3 카메라와 테스트 환경

- iOS Simulator와 Android Emulator는 실제 카메라 동작을 완전히 대체하지 못할 수 있다.
- 카메라 기능은 가능하면 양쪽 실기기에서 테스트한다.
- 시뮬레이터에서는 사진 보관함 선택이나 테스트용 fixture를 대체 경로로 사용한다.
- 카메라 preview 비율, 상태바, Safe Area, 화면 회전 처리에서 플랫폼별 차이가 드러날 수 있다.

### 6.4 뒤로가기와 화면 생명주기

- Android에는 시스템 뒤로가기 버튼/제스처가 있어 WebView history, 작성 중인 폼, 모달의 우선순위를 정해야 한다.
- iOS는 navigation bar의 뒤로가기와 swipe-back 제스처를 중심으로 처리한다.
- 앱이 background로 이동했다가 돌아오는 경우 카메라 preview, WebView, 작성 중인 데이터가 정상적으로 복구되는지 확인한다.

### 6.5 WebView 네트워크와 보안

- iOS는 ATS(App Transport Security) 정책의 영향을 받아 HTTP 리소스가 기본적으로 제한될 수 있다.
- Android는 cleartext traffic 설정과 network security 정책의 영향을 받을 수 있다.
- cookie·localStorage·인증 상태가 두 플랫폼에서 동일하게 보존된다고 가정하지 않는다.
- 허용 domain과 외부 링크 정책을 플랫폼별 설정에 흩어놓지 말고 앱 코드의 allowlist로 관리한다.

### 6.6 공유와 딥링크

- 공유 대상 MIME type과 파일 URI 처리 방식이 iOS와 Android에서 다를 수 있다.
- iOS는 URL scheme과 Universal Links, Android는 intent filter와 App Links로 확장된다.
- 첫 버전은 `nativelab://` custom scheme으로 학습하고, 운영 수준에서는 HTTPS 기반 Universal Links/App Links를 별도로 학습한다.
- 앱이 종료된 상태에서의 초기 URL과 실행 중 수신되는 URL을 모두 처리해야 한다.

### 6.7 UI와 접근성

- 기본 폰트, line height, ripple/touch feedback, 그림자 표현이 플랫폼별로 다르다.
- Android의 system back, 키보드 resize 방식, edge-to-edge 정책을 별도로 확인한다.
- iOS의 Safe Area와 swipe-back 제스처를 고려한다.
- 플랫폼별 차이를 무조건 CSS 값으로 숨기기보다, 사용성 차이가 있는 경우 `Platform.select` 또는 분리 컴포넌트로 의도를 드러낸다.

## 7. 구현 전 결정사항

- 실행 방식: Expo 중심으로 시작한다.
- 우선 플랫폼: iOS 실기기/시뮬레이터를 기준으로 하고 Android를 후속 검증한다.
- 저장 방식: 기록 메타데이터는 SQLite, 실제 첨부파일은 앱 전용 파일 시스템에 저장한다.
- WebView 비중: 메인 화면이 아닌 학습용 보조 화면으로 제한한다.
- 첫 버전 범위: 카메라·사진/파일 선택·로컬 저장·공유·딥링크/WebView Bridge까지다.
- 추후 범위: 위치·알림·생체 인증·백그라운드 작업·푸시·Bluetooth 등은 별도 학습 과제로 둔다.

이 문서는 구현 전 기준 문서다. 실제 코드 작업은 별도의 작업지침과 우선순위를 받은 뒤 시작한다.
